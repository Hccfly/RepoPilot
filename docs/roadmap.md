# 实施路线图

## P0——只读仓库规划

状态：**已完成**。

目标：在不修改仓库的前提下，把用户任务转换成有证据支撑的结构化计划。

需要实现：

- 使用 `rg` 实现 `search_code`，遵守 Git 忽略规则和结果数量限制。
- 根据已跟踪文件和相关文件生成仓库清单，排除依赖目录与构建产物。
- 实现兼容 OpenAI 接口、支持依赖注入的 `ModelClient` 适配器。
- 实现 Explorer 和 Planner 节点，填充 `Evidence` 与 `ChangePlan`。
- 增加 `repopilot plan <goal>` 命令以及结果确定的 mock 模型测试。

验收标准：

- 每个计划步骤都引用实际检查过的文件。
- P0 测试必须阻断网络，并且不能改变 fixture 的任何字节。
- 模型返回空内容或无效内容时，工作流进入明确可见的失败状态。
- 拒绝读取大文件、密钥文件、`.git` 和仓库外路径。

实现位置：`tools/repository.py`、`llm.py`、`planning.py`、`runtime.py` 和 `cli.py`。
离线测试覆盖正常规划、空输出、非法文件引用、ignore 规则、敏感文件过滤和只读不变性。

## P1——经过审批的补丁生命周期

状态：**已完成**。

目标：先让用户审查待修改内容，获得批准后再应用最小补丁。

需要实现：

- 实现结构化补丁提案或 unified diff 解析器。
- 校验 hunk 对应的原始内容，并以原子方式替换文件。
- 记录初始 Git 状态，保护用户原本就存在的改动。
- 实现 `WAIT_APPROVAL`、`/apply`、`/diff` 和 `/undo`。
- 建立补丁台账，记录 hash、涉及文件、正向 diff 和反向 diff。

验收标准：

- hunk 冲突时整体失败，不能留下部分写入结果。
- 撤销后文件能够逐字节恢复。
- 不能静默覆盖属于用户的未提交修改。
- 路径穿越或密钥文件补丁必须在写入前被拒绝。

实现位置：`editing.py`、`patching.py`、`persistence.py`、`git.py`、`runtime.py` 和 `cli.py`。
离线测试覆盖新增、修改、删除、脏文件保护、提案后冲突、多文件整体失败、审批、外部台账、
路径穿越、密钥文件、跨路径补丁和逐字节撤销。

## P2——验证与 checkpoint 恢复

状态：**已完成**。

目标：证明补丁确实有效，并且任务中断后能够安全恢复。

需要实现：

- 首先支持识别 Python 和 Node 项目。
- 提供 `pytest`、`ruff`、`npm test`、`npm run lint` 等显式验证动作。
- 使用 argv 执行命令，不经过 Shell；同时支持超时、输出限制和退出码捕获。
- 实现 SQLite `RunStore` 以及 resume/status/list 命令。
- 持久化编辑和验证操作的审批结果。

验收标准：

- 验证命令失败后，任务不能进入 `DONE`。
- 超时进程必须被终止，并在结果中明确报告。
- 重启 CLI 后仍然保留计划、审批、补丁回执和验证历史。
- 恢复任务后，已经完成的工具不能重复执行。

实现位置：`verification.py`、`persistence.py`、`contracts.py`、`runtime.py` 和 `cli.py`。
离线测试覆盖项目识别、白名单解析、argv 执行、输出截断、超时终止、失败阻断 DONE、
审批拒绝、逐动作落盘、SQLite 台账往返和 CLI 列表/状态。

## P3——有限修复与评测

状态：**已完成**。

目标：把安全工作流完善成可信的 Coding Agent 产品演示。

需要实现：

- 默认最多执行一次修复重试。
- 增加符号感知的 Repo Map 和变更影响上下文。
- 增加独立于 Editor 上下文的只读审查节点。
- 生成 JSON/Markdown 运行报告，包含证据、diff 摘要、命令、耗时和停止原因。
- 建立 fixture 基准，覆盖 Bug 修复、小功能开发、审查、冲突、超时和恢复场景。

验收标准：

- 重试次数和工具调用预算必须是确定的。
- 出现无关修改时，评测分数应当降低。
- 最终答案中的结论必须关联到 diff 或验证证据。
- 不使用 API Key 也能复现基准测试结果。

实现位置：`repair.py`、`repo_map.py`、`review.py`、`report.py`、`benchmark.py`、`verification.py`
和 `cli.py`。离线测试覆盖符号提取与影响面、修复预算与范围限制、审查结论与路径校验、报告证据链、
五个基准场景和无关修改扣分。

## P4——模型与 Provider 插件系统

状态：**已完成**。

目标：让模型接入可替换，并且不修改核心代码就能新增第三方 Provider。

需要实现：

- Provider 注册表，内置 `deepseek`、`openai`（任意 OpenAI 兼容端点）和 `anthropic`。
- 基于 `repopilot.model_providers` entry point 的插件发现。
- 按 Provider 约定解析凭据、模型名和地址，密钥不进入配置对象、检查点或日志。
- `repopilot providers` 命令和全局 `--provider` 覆盖参数。

验收标准：

- 加载失败的插件不得阻止内置 Provider 工作。
- 插件不能覆盖内置同名 Provider。
- 离线测试不读取进程环境、不请求网络即可验证注册、解析与就绪判断。

实现位置：`providers.py`、`llm.py`、`config.py`、`runtime.py` 和 `cli.py`。

## P5——交互式终端界面

状态：**已完成**。

目标：在同一会话里完成计划、审批、验证和审查，同时不削弱已有的安全边界。

需要实现：

- 仅用标准库实现的 REPL 面板，命令与 CLI 一一对应。
- 运行摘要、diff 预览和验证历史的内联渲染。
- `apply` / `undo` 的显式确认，且不绕过策略层。
- 非 TTY 时关闭 ANSI 颜色，便于脚本与测试。

验收标准：

- 未知命令给出可读错误，会话不中断。
- 拒绝确认时不得写入任何文件。
- 离线测试可在临时仓库上跑通 propose → apply → verify → review → report。

实现位置：`tui.py`、`cli.py`，共享渲染逻辑位于 `providers.py` 与 `report.py`。

## P6——并行只读探索与独立验证执行

状态：**已完成**。

目标：缩短大仓库上的探索与验证耗时，同时保持结果可复现。

需要实现：

- 有界并发原语，结果按输入顺序返回，异常按输入顺序回传。
- Explorer 并行执行多条检索与多个文件读取，证据顺序与串行一致。
- 验证动作在独立子进程中并行执行，逐动作落盘且历史顺序固定。
- `rg` 使用确定性排序，避免多线程遍历导致证据顺序抖动。

验收标准：

- 串行与并行模式的证据、读取文件和查询列表完全一致。
- 动作确实重叠执行（屏障验证），但历史顺序与选定顺序一致。
- 单个动作失败或无法执行不中断其他动作，且仍阻止进入 `DONE`。

实现位置：`concurrency.py`、`planning.py`、`verification.py`、`tools/repository.py` 和 `config.py`。

## P7——经过单独审批的可选 Git 提交

状态：**已完成**。

目标：在证据齐全的前提下，提供一个默认关闭、必须显式触发的最小 Git 提交能力。

需要实现：

- 复用 `git_write` 策略，默认 `deny`。
- 只提交本次运行涉及的文件，不影响用户已暂存的其他改动。
- 提交前要求阶段为 `DONE`，且文件哈希仍与应用回执一致。
- 记录提交回执（SHA、说明、文件、时间）并纳入运行报告。

验收标准：

- 默认策略下拒绝提交，仓库 HEAD 不变。
- 用户已暂存的其他文件在提交后仍保持暂存且未被提交。
- 应用后文件被再次修改时拒绝提交。
- 提交后禁止 `undo`。

实现位置：`git.py`、`patching.py`、`editing.py`、`report.py`、`cli.py` 和 `tui.py`。

## P8——远程沙箱与 CI 集成

状态：**已完成**。

目标：让验证能在隔离环境执行，并让 RepoPilot 以无交互方式接入 CI。

需要实现：

- 可插拔执行后端：本地子进程，或固定的 argv 前缀（容器/远程包装器）。
- 前缀不经过 shell，动作 argv 只能追加，`{workspace}` 作为单个参数替换。
- `repopilot ci plan|propose|verify`：无交互、稳定退出码、写出产物。
- CI 模式永不 apply、永不 push。

验收标准：

- 前缀模式不会合并成 shell 字符串，带空格的参数保持独立。
- 未知沙箱模式或空前缀给出明确错误。
- `ci propose` 只写产物不改文件；`ci verify` 未通过时退出码为 `1`。
- 产物包含 `patch.diff` 与 `report.json`。

实现位置：`config.py`、`verification.py`、`ci.py`、`runtime.py` 和 `cli.py`，使用说明见
[`docs/ci.md`](ci.md)。

## P9——独立沙箱服务协议

状态：**已完成**。

目标：把验证执行从"argv 前缀"升级为可独立部署的服务，客户端只发动作名。

需要实现：

- TCP + 换行分隔 JSON 的最小协议；请求只含动作名、token 与超时。
- 服务端用自己的白名单解析 argv，客户端提供的任何命令字段一律忽略。
- token 鉴权、请求/响应大小上限、超时钳制与输出上限。
- `repopilot sandbox serve` 命令与 `mode = "remote"` 配置。

验收标准：

- 客户端无法通过协议执行白名单之外或任意命令。
- 非法 JSON、超大请求、错误 token 都不会导致服务崩溃。
- 经过真实 pytest 的端到端调用通过。

实现位置：`sandbox.py`、`config.py`、`runtime.py` 和 `cli.py`，协议说明见
[`docs/ci.md`](ci.md)。

## P10——沙箱 TLS 与多租户调度

状态：**已完成**。

目标：让沙箱服务能安全地跨网络暴露，并在多个仓库之间隔离与限流。

需要实现：

- 租户注册表：名称 → 工作区、白名单、token、并发上限。
- 调度器：全局与每租户信号量，超限返回 `busy` 且容量及时释放。
- TLS 1.2+：服务端证书链/私钥，客户端 CA 校验。
- 每租户 token 环境变量及 `default` 租户的回退规则。

验收标准：

- 错误 token 不能跨租户执行动作。
- 并发上限生效，且容量在请求结束后释放。
- TLS 握手成功路径可用；不受信证书与明文客户端都会被拒绝。
- 非回环绑定仍强制要求 token。

实现位置：`sandbox.py`、`config.py` 和 `cli.py`，使用说明见 [`docs/ci.md`](ci.md)。

## P11——Docker 容器后端

状态：**已完成**。

目标：把单个验证动作放进一次性容器执行，获得确定的文件系统与网络隔离。

需要实现：

- `mode = "docker"` 后端：`docker run --rm`，工作区挂载到 `/work`。
- 镜像、网络、内存、CPU、用户可配，并逐项校验防止参数注入。
- 超时后 `docker kill` 容器，不留孤儿进程。
- 复用现有白名单、输出上限、并发执行与租户机制。

验收标准：

- 动作在挂载的工作区内执行，退出码正确透传。
- 超时会终止容器且 `docker ps -a` 中无残留。
- 非法镜像或选项值给出明确错误。

实现位置：`sandbox.py`、`config.py`，使用说明见 [`docs/ci.md`](ci.md)。

## P12——容器池与镜像预热

状态：**已完成**。

目标：在并发验证时把容器创建开销移出关键路径，并提供可控的镜像预热策略。

需要实现：

- `pool_size > 0` 启用容器池：后台线程补充空闲容器，动作通过 `docker exec` 执行。
- 每个动作仍独占一个容器，结束后后台销毁并补充，隔离不回退。
- `pull = never | missing | always` 控制镜像预热，失败即报错。
- 进程退出时通过 `atexit` 清理池内容器。

验收标准：

- 池化运行的结果、退出码与超时行为与每动作容器一致。
- 串行与并行运行后 `docker ps -a --filter label=...` 均为空。
- 动作之间不共享容器内状态（`/tmp` 写入不跨动作可见）。
- 实测数据记录在文档中，说明串行场景不应开启池化。

实现位置：`sandbox.py`、`config.py`，使用说明见 [`docs/ci.md`](ci.md)。

## P13——沙箱请求审计与配额持久化

状态：**已完成**。

目标：让沙箱服务的每次调用可追溯，并让租户配额跨重启生效。

需要实现：

- SQLite 审计表：时间、租户、动作名、结果、退出码、耗时、客户端地址。
- 审计不记录 token 与命令输出。
- 固定窗口配额计数器，按租户持久化，重启后继续生效。
- `sandbox audit` 与 `sandbox quota` 查看命令。

验收标准：

- 成功、失败、未授权、未知租户的请求都会进入审计。
- 数据库文件中不出现 token。
- 配额用尽后拒绝请求，新进程读取同一文件仍拒绝。
- 窗口滚动后额度恢复。

实现位置：`sandbox_audit.py`、`sandbox.py` 和 `cli.py`，使用说明见 [`docs/ci.md`](ci.md)。

## P14——人审批的自我改进（RSI）

状态：**已完成**。

目标：让 RepoPilot 针对自身的基准失败提出改进，并在隔离副本中验证效果；是否应用由人决定。

需要实现：

- 独立评测器：候选在子进程里用自己的 `src` 运行，只上报运行事实。
- 独立 `grader.py`：唯一打分点，规则为代码常量；候选进程不参与打分。
- 指纹校验：候选与基线的 grader/benchmark 指纹不一致即拒绝评分；`--expect-grader` 支持外部锚点。
- 范围守卫：只允许改 `src/repopilot/**`，禁止测试、文档与评分实现。
- `rsi eval` / `rsi compare` / `rsi propose` 三个命令，输出 scorecard 与候选补丁，不自动应用。

验收标准：

- 无关补丁不改变分数；引入语法错误的补丁被评为回退。
- 越界补丁在评测前被拒绝；修改评测栈的候选被判 0 分。
- scorecard 同时包含基线与候选、指纹，并标记回退。
- 应用候选补丁仍然需要显式的 `apply`。

实现位置：`rsi.py`、`grader.py`、`benchmark.py`、`cli.py`，说明见 [`docs/rsi.md`](rsi.md)。

## P15——多轮 RSI 与历史 scorecard

状态：**已完成**。

目标：连续生成候选、保留每轮结果，并避免重复提交同一个补丁。

需要实现：

- 固定基线只评测一次，候选逐轮在副本上评测。
- 上一轮失败原因作为反馈进入下一轮目标。
- 补丁 sha256 去重；每轮状态 `improved` / `rejected` / `duplicate` / `error`。
- JSON Lines 历史与每轮 diff 落盘；`rsi run` / `rsi history` 命令。
- 任何一轮都不自动应用补丁。

验收标准：

- 两轮不同候选都会记录，源文件逐字节不变。
- 相同候选在第二轮标记 `duplicate` 且跳过评测。
- 单轮失败记录 `error` 并停止循环。
- `best_score` 达到 1.0 时提前结束。

实现位置：`rsi.py`、`rsi_history.py`、`cli.py`，说明见 [`docs/rsi.md`](rsi.md)。
